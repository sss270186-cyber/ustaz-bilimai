# Бірінші кезеңді қауіпсіз қосу

## Сақтау және қалпына келтіру

Бастапқы commit: `f9cc0a518d326e0831b152e1e88b643175e5a597`.
GitHub резервтік тармағы: `backup/before-stage1-2026-10-18`.

Кодтың Git bundle және tar.gz архивтері жұмыс ортасының `work/backups/` каталогына сақталды. Бұлар Supabase дерекқорының резервтік көшірмесі емес. Осы кезеңде тірі деректер өзгерген жоқ.

Миграцияны тірі базаға қолданар алдында Supabase-тің backup/PITR мүмкіндігімен немесе database connection арқылы `supabase db dump`/`pg_dump` көмегімен **дерекқор мен Auth схемасының толық қалпына келетін көшірмесін** жасаңыз. Сақталған backup-ты бөлек staging жобасына қалпына келтіріп тексеріңіз. Service role REST кілті толық `pg_dump` жасауға жеткіліксіз. Аккаунт құпиясөздерін бұл репозиторийге, архивке немесе чатқа енгізбеңіз.

## Staging

1. Өндірістік деректердің сақталған көшірмесі барын тексеріңіз. Staging үшін бөлек Supabase жобасын және тест аккаунттарын қолданыңыз.
2. Бастапқы жобадағы `profiles` бағандарының барын тексеріңіз: `id`, `role`, `username`, `full_name`, `class_name`, `created_at`. Код дәл осы бар схемаға сүйенеді. `profiles` ескі RLS саясатын және `is_teacher()` функциясын бөлек тексеріңіз: бастапқы репозиторийде олардың DDL файлы жоқ.
3. `supabase/migrations/202610180001_learning.sql`, содан кейін `202610180002_measurement_seed.sql`, `202610180003_answer_formats.sql`, `202610180004_full_curriculum.sql`, `202610180005_quality_review.sql` файлдарын ретімен орындаңыз. Supabase CLI migration tracking немесе SQL Editor журналы пайдаланылады. Бұл файлдарды қайта-қайта орындамаңыз; олар бұрыннан бар объектінің үстінен жазуды әдейі жасамайды.
4. Бірінші миграция қолданыстағы мұғалімдерді `unt_teachers` тізіміне көшіреді. Бір мұғалім болса, бұрынғы барлық оқушы оның оқу тобына қосылады. Бірнеше мұғалім болса, топ байланыстары автоматты тағайындалмайды. Мұғалім бар оқушыны кабинеттегі «Топқа қосу» арқылы байланыстырады. Бұл мүмкіндікті осы платформаның аккаунт әкімшілері ғана қолданады; бөлек ұйымдар үшін оқушыны иелену моделі келесі кезеңде қажет.
5. Жаңа мұғалімді `unt_teachers` тізіміне тек сенімді database owner қосады. Клиенттен өз рөлін өзгерту арқылы мұғалім болу мүмкін емес. Мұғалім құқығын қайтарып алғанда осы тізімді де жаңарту қажет.
6. Vercel Preview-ге `.env.example` ішіндегі айнымалыларды staging мәндерімен орнатыңыз. `SUPABASE_SERVICE_ROLE_KEY` ешбір public/VITE/NEXT_PUBLIC айнымалыда болмауы тиіс.
7. `npm ci`, `npm run check`, `npm run seed:check`, `npm test`, `npm run test:ui` орындаңыз. Одан кейін Vercel Preview-де нақты staging Auth-пен қолмен төмендегі тізімді тексеріңіз.

## Нақты staging қабылдау тексеруі

- Бұрынғы мұғалім email/құпиясөзбен, бұрынғы оқушы сол логин/құпиясөзбен кіре алады.
- Мұғалім жаңа сынақ оқушысын тіркейді; жаңа оқушы кіре алады; құпиясөз жауапта/логта қайтарылмайды.
- Екі бөлек оқушының нәтижелері бір-біріне көрінбейді. Мұғалім тек өзінің оқу тобының нәтижесін көреді.
- B: 2, C: 10 тапсырма. Бір жауап дұрыс, бір жауап қате берілгенде жеке шешімі ашылады; қайта кіргенде нәтижелер қалады.
- Network response-та workspace/tasks ішінде `answer`/`steps` жоқ; шешім тек `unt_submit_answer` нәтижесінде келеді.
- Клиент кілтімен `unt_private.answer_keys` оқу, `unt_attempts`-ке тікелей INSERT/UPDATE, `unt_teachers`-ке INSERT өтпейді.
- Анонимді пайдаланушы тапсырма/нәтиже оқи алмайды. Бір минутта 20 тексеруден кейін шектеу іске қосылады.
- Жасырылған тапсырма оқушыдан жоғалады; бұрынғы әрекеттер сақталады.
- ҚМЖ үлгісі жұмыс істейді; HTML енгізілгенде мәтін болып шығады. Бұрынғы `bilimai_results` жергілікті деректері өшпейді.
- Vercel Preview-де `/scripts/measurement.cjs`, `/supabase/migrations/202610180002_measurement_seed.sql`, `/api/_lib/supabase.cjs`, `/app.py`, `/tests/database.test.cjs`, `/.env` ешбір бастапқы кодты бермеуі тиіс (404/403). Preview response-та CSP және no-store тақырыптарын тексеріңіз.
- Телефон мен компьютерде тапсырма енгізу, нәтиже көру және жүйеден шығу жұмыс істейді.

## Production және кері қайту

Staging қабылдау тексеруінен және пайдаланушының Production өзгерісіне бөлек нақты растауынан кейін ғана жаңа толық backup жасап, миграцияларды Production-ға қолданыңыз; ескі профильдер мен аккаунт санын салыстырыңыз. Production-ға миграция қолдану немесе кодты жариялау алдында пайдаланушының бөлек нақты растауын алыңыз. Staging сынағына берілген рұқсат Production өзгерісіне рұқсат болып саналмайды. Бұл жұмыста migration/deployment автоматтандырылған жоқ.

Қате болса, Vercel-дің бұрынғы deployment-іне оралыңыз немесе бастапқы commit-ті қайта жариялаңыз. Жаңа `unt_…` кестелерін жоймаңыз: оларда жиналған әрекеттерді сақтаңыз. Миграциялар `profiles`, `auth.users` және бұрынғы ҚМЖ деректерін өзгертуге арналмаған. Жоба күтпеген SQL қатесін берсе, транзакция rollback болады; seed-тің бірінші миграциядан бөлек транзакция екенін ескеріңіз.

## Автоматты нақты staging сынағы

`npm run test:staging` тек бөлек hosted Supabase жобасы мен Vercel Preview үшін арналған. Ол Production хостын қабылдамайды және бірінші GET `/api/config` арқылы Preview-дің дәл staging базасына қосылғанын тексермейінше аккаунтқа кірмейді, дерек жазбайды.

Ортаның қорғалған айнымалыларына мыналарды орнатыңыз (чатқа немесе GitHub файлына енгізбеңіз):

- `STAGING_SUPABASE_URL`
- `STAGING_SUPABASE_PUBLISHABLE_KEY`
- `STAGING_PREVIEW_URL`
- `STAGING_TEACHER_EMAIL`
- `STAGING_TEACHER_PASSWORD`

Миграцияға дейін staging-де teacher рөлі бар сынақ профилін дайындаңыз; миграция сол мұғалімді `unt_teachers` тізіміне көшіреді. Алдымен барлық бес миграция қолданылған және 228 тапсырманың бәрі ашық болуы керек. Басқару кілтін клиентке берудің қажеті жоқ: сынақ мұғалімі екі synthetic оқушыны қолданыстағы сервер API-імен тіркейді.

Сынақ нақты Auth кіруін, оқушы тіркеуді/топқа қосуды, дұрыс/қате жауапты, жаңа сеанстан кейін тарихты, екі оқушы арасындағы RLS-ті, жауап кілтін қорғауды, мұғалім құқығын және жасыру/ашуды тексереді. Жасырылған тапсырманы `finally` ішінде қалпына келтіреді. Сынақ аккаунттары мен әрекеттері сақталады; пайдаланушыны не нәтижені жоймайды. Жаңа құпиясөздер тек жадта тұрады, логқа шығарылмайды. Бұл smoke-ті Production-да орындамаңыз.

```sh
npm run test:staging
```

Proxy қолданылатын Node.js 24 ортада inherited proxy сақталуы тиіс (`NODE_USE_ENV_PROXY=1` қажет болуы мүмкін). Бұл механизм желілік allowlist-ті айналып өтпейді: staging және Preview домендері орта конфигурациясында рұқсат етілуі керек.

**Басқару қолжетімділігі:** толық backup/restore мен жоба жасау үшін `SUPABASE_ACCESS_TOKEN` және database-owner connection (`SUPABASE_DB_URL`), Preview айнымалыларын өзгерту үшін `VERCEL_TOKEN` керек. Нақты жобаға шектелген токендерді қорғалған ортаға беріңіз. Желілік саясатқа `api.supabase.com`, `api.vercel.com`, staging/Preview домендері және қолданылатын PostgreSQL host/port рұқсаттары қосылуы қажет. App service_role кілті бұл басқару қолжетімділігін алмастырмайды.
